# Security

Version 1.0.0. This document exclusively owns security, privacy, authorization, disclosure and assurance policy. The user's 2026-10-13 instruction to answer remaining questions using defaults explicitly adopts SEC-AUTH-03, SEC-AUTH-04 and the least-privilege clauses previously labeled proposals. Existing stronger rules remain in force. This is approved specification policy; no implementation, penetration test or compliance certification is claimed.

## Security posture

One operator deployment, invited admin accounts, no player accounts, no passwords and no external business-data integration. The service protects public-record integrity, internal commerce, account credentials/sessions, operational secrets and audit evidence. All clients and their inputs are untrusted. Platform/cloud security assumptions require verification at release. A compromised authorized admin can enter a factually false but structurally valid score or sale; attribution, restricted audit evidence and revocation are the accepted launch treatment (T-26). There is no second-person score approval or automatic factual truth detector.

The supplied secure-coding references are frozen in [the source manifest](docs/security-sources/manifest.json): [S-NODE](docs/security-sources/S-NODE.md), [S-REACT](docs/security-sources/S-REACT.md), [S-NATIVE](docs/security-sources/S-NATIVE.md), [S-JS](docs/security-sources/S-JS.md), [S-TS](docs/security-sources/S-TS.md). Their original paths, labels and hashes preserve provenance. Adopt their applicable defensive outcomes; a source's runtime label does not override ARCHITECTURE. Node26/RN0.87-specific APIs are not assumed on Node24/RN0.86. TypeScript7-only compiler/API changes do not apply to TypeScript6; strict-family, noUncheckedIndexedAccess, exactOptionalPropertyTypes, useUnknownInCatchVariables, noImplicitOverride, noFallthroughCasesInSwitch, noImplicitReturns, noCheck=false, explicit ambient types and boundary validation do apply. No `any`, unchecked assertions, ts-ignore or ts-nocheck at trust boundaries. SSR/RSC, rich HTML, WebViews, custom deep links, uploads, push, AI and payment credentials are excluded and their feature-specific controls are evaluated nonapplicable. No supplied baseline is weakened by choosing an older compatible runtime line.

## Access and disclosure policy

**SEC-ACCESS-01 — Server authority.** The API MUST independently validate current identity, grant, action, object relationship and field permission on every protected request. Hidden UI, supplied role labels, object UUIDs, origin headers and native platform labels confer no grant. Reject unlisted actions/fields; deny failed or unavailable security decisions under SEC-FAIL-01. Shared database account locking prevents concurrent revocation from racing past admitted mutations: a revocation waits for earlier admitted operations, then later operations MUST fail.

**SEC-ACCESS-02 — Explicit grants.** Admin means an enabled account with the server-held admin flag. Audience categories grant nothing. All admins share one deployment's business authority; no per-organizer ownership partition exists.

| Actor | Permitted operations and fields |
| --- | --- |
| Anyone, including anonymous | Tournament list/direct detail (including empty drafts and assigned display names from creation), plan, scores, statistics, world/local rankings, and public deployment contact information |
| Current admin | All listed business commands/commerce and player reads, account list, admin invitations/revocation/disablement, privacy erasure; subject to state/version rules and fresh-proof restrictions below |
| Enabled account, including revoked admin | Own session and safe credential metadata; own passkey maintenance; logout; public reads. No business mutation/commerce/account-list access without current admin grant |
| API runtime workload | Only defined database reads/writes and audit append function; no schema changes, audit update/delete, bucket deletion or native signing |
| Maintenance workload | Expiry/retention and audit export/check functions only; no admin enrollment or arbitrary business mutation |
| Deployment operator | Separate MFA-protected cloud/CLI authority for bootstrap, disaster recovery, secrets, deployments and audit investigation. Not an application sign-in fallback |

Public tournament fields are exactly the public shapes in ARCHITECTURE Read catalog: metadata, court labels, seed numbers, ranking-source label, participation/player UUIDs and display names, match references/status/scores/winners and timestamps, champion and derived statistics. Public ranking entries include player UUID/display name/position/tie flag and snapshot provenance. Reasons for cancellation, retirement, correction, stock changes or privacy erasure, account links, actor IDs, operation references, credentials, sessions, commerce, logs and raw storage fields MUST NOT enter public projections. Participants need no account association; such an association is not stored. Display names can be pseudonyms. Direct archived reads follow retention; there is no public player directory. No extra fields are public merely because they exist in a storage record.

Every protected write requires current authority even on replay. Only the creating enabled account can read its operation outcome; an account lacking admin authority can retrieve only its own credential-lifecycle outcomes; other accounts get indistinguishable404. Standard admin account lists expose safe display_name/status/version, not passkey metadata of others. Own credential metadata excludes public keys/credential raw IDs. Only the operator audit-reader IAM role reads audit evidence; ordinary app admins have no audit API. Changing an admin grant, invitation, disabling/erasing an account, or a credential requires successful account-bound passkey proof no more than five minutes old. Player erasure also requires this fresh proof. Business scoring/commerce uses the normal session lifetime.

## Authentication and credential lifecycle

**SEC-AUTH-01 — Passkey only.** Every application sign-in and reauthentication MUST use a verified passkey with user verification. Passwords, email/SMS codes, magic links, security questions and support sign-in overrides MUST NOT exist. Invitation tokens authorize initial registration only; they cannot access an existing account or create a session without a newly verified passkey. Operational cloud IAM is separate service/operator authority, never a way to impersonate an existing application account.

**SEC-AUTH-02 — Optional second device.** After first registration and in account settings, show: `Set up access on a second device so you can still sign in if you lose this one.` Provide `Add a passkey` and `Continue`. One passkey completes registration. Store credential label, creation/last-used times and authenticator backup flags, but never claim credential count proves two independent devices. Synced passkeys are permitted. Unsupported devices get an explanation and a link to use a supported browser/device, without weaker authentication.

**SEC-AUTH-03 — Verification.** Use the ARCHITECTURE verifier, not custom crypto. Generate32 cryptographically random challenge bytes; expire after five minutes; bind type, account/invitation context, platform and exact expected origin; consume once atomically on successful verification. Invalidate a ceremony after five failed submissions. At most five outstanding ceremonies per account/invitation; new options invalidate the oldest. Registration: residentKey required, userVerification required, attestation none, algorithms ES256(-7) and RS256(-257), no authenticatorAttachment restriction. Authentication requires user presence and verification, valid type/challenge/RP hash/origin, credential ownership and signature. Origin allowlist is exact configured HTTPS APP_ORIGIN plus the associated native origins; Android `android:apk-key-hash:` values derive from approved release certificates, iOS uses the associated HTTPS RP origin. Bind native origin selection to the challenge, never trust a claimed platform alone. Reject cross-origin ceremonies and unapproved extensions. Counter handling follows the verifier: nonzero counter regression fails; zero counters for synced credentials remain supported, with backup-state changes recorded. No attestation-based device vendor restriction.

Verify domain ownership, apple-app-site-association, Android Digital Asset Links and actual release signing builds before native promotion. Development exceptions are limited to the separate development origin. Verification is based on [WebAuthn Level 2 registration/assertion procedures](https://www.w3.org/TR/2021/REC-webauthn-2-20210408/); challenge single-use and required verification are project choices within that protocol.

**SEC-AUTH-04 — Enrollment and maintenance.** First admin is created by an operator's protected `pnpm operator bootstrap` CLI: only when no enabled admin exists, under a global identity lock, generate a32-byte one-use invitation valid15 minutes; consume it only after passkey registration. Do not ship a default account. Existing admins invite a new administrator with a normalized display name1–80 and a32-byte token valid24h. The inviter attests the intended recipient's authority and delivers the token outside the app. No email is sent by the application. The invitation is bound to its issuer and is invalid when that issuer loses authority; bootstrap invitations are bound to the operator audit event. One outstanding bootstrap invitation maximum; rerunning explicitly revokes its predecessor. Ordinary invitations may be explicitly revoked through `pnpm operator revoke-invitation --id` or by disabling/revoking their issuer; no resend/recovery magic links.

Enrollment creates a new UUID account and first credential atomically, consumes the invitation and establishes its admin grant. Display names are not unique identity proof. Existing accounts cannot be linked by name or invitation. Add/remove/rename only one's own credentials with fresh proof and account version; maximum 10 active credentials; last active credential cannot be removed. Adding/removing a credential revokes all prior account sessions and returns a newly authenticated current session only after the same fresh proof; clients update their credential/session state atomically. Disabled accounts and revoked credentials cannot authenticate. Changing an admin to nonadmin does not grant a new role. Regrant/reactivation is excluded at launch; an operator can invite a new account instead. Deny any ordinary action that would leave zero enabled admins, including self-disable/revoke/erasure.

If all passkeys are lost, the old account is not recoverable. A remaining admin disables the old account and may invite a new account. If no usable admin remains, the operator runs an audited break-glass CLI using separate cloud authority to disable inaccessible admins and create a NEW bootstrap invitation/account; it never attaches a credential to or authenticates as the old account. Require operator reason and an explicit `--replace-inaccessible-admins` switch. Revoke old sessions and invitations before issuing the new invitation. A compromised operator can control deployment; app controls do not claim to defend against that ultimate authority.

## Sessions and transport

**SEC-SESSION-01.** Sessions are32 random byte opaque reference tokens; store SHA-256 hashes, never plaintext bearer/cookie values. Maximum absolute life8h, idle life30min, fresh-proof window5min, at most five active sessions/account (sixth revokes oldest by creation time/UUID). Every authenticated read/write validates server state, enabled flag and current grant; public polling does not renew an admin's idle timer unless sent through a protected endpoint. Rotate token on login/reauthentication and invalidate the old token. Current-session logout invalidates server state and expires local cookie/token; if offline, immediately clear local state and retry remote revocation on next connectivity without restoring the token to UI. Revocation/disablement/account erasure invalidates all account sessions; credential removal/addition rotates as above.

Browser session: `__Host-aa_session`, Secure, HttpOnly, SameSite=Strict, Path=/, no Domain. Every cookie-authenticated POST requires exact allowed Origin and an independent32-byte CSRF token in `X-CSRF-Token`, compared in constant time with the session-bound hash. `/session` returns its session's CSRF token derived as HMAC(session id, dedicated32-byte `CSRF_HMAC_KEY`); store only its hash. Enrollment/sign-in have exact-origin checks and single-use ceremony binding before sessions exist. No browser credential in localStorage/sessionStorage/IndexedDB. Native stores bearer only in expo-secure-store with iOS WHEN_UNLOCKED_THIS_DEVICE_ONLY and Android Keystore backing, excluded from backups. No refresh token/JWT. Native uses Authorization Bearer; valid bearer validation, not a client-type header, determines that cookie-CSRF rules are inapplicable. Reject simultaneous bearer and session cookie. All authenticated client caches are in memory and keyed by account/session generation; clear on logout/401/identity change and ignore late responses from prior generations. No service worker or persistent API cache.

**SEC-TRANSPORT-01.** Require verified TLS1.2+ externally, preferTLS1.3, HTTPS-only release clients and verified TLS to RDS. Do not disable certificate or hostname verification. ALB termination and private-network roles follow ARCHITECTURE. The API only trusts forwarding headers from the ALB's configured subnets/security boundary, with one proxy hop and validated host. Browser API is same-origin; do not grant CORS access to other origins. Association files are public static exact-origin assets. Native certificate pinning is not used: platform trust and certificate validation avoid an extra rotation/recovery failure mode. Production HSTS `max-age=31536000; includeSubDomains` requires operator confirmation that all subdomains support HTTPS before promotion; no preload submission is automatic.

## Input and data integrity

**SEC-INPUT-01.** Validate every command, received API response, configuration, stored client value and native-module response against a closed runtime schema at its receiving boundary. Types alone grant no trust. Reject unknown properties, prototype keys, duplicate JSON keys, malformed UUIDs/times/enums, unbounded arrays, invalid number precision and unsupported fields without mutation. Validate read-back text/relations before projecting. Normalize text per REQUIREMENTS. Never bind a body to a DB row, accept computed client totals/winners as authority, use untrusted URLs/props as code, or dynamically select modules/query structure from arbitrary input. A response failing client validation is an unavailable-data error, never render partially trusted data.

**SEC-DATA-01.** Use bound SQL values, fixed query structures and DB foreign keys/range constraints backing server domain checks. Adopt separate runtime, migration, maintenance and read-only audit roles. Runtime has only SELECT/INSERT/UPDATE/DELETE on necessary business tables and EXECUTE on append-audit function; no DDL, role grants, audit mutation or raw file execution. Worker uses defined maintenance functions; migration identity is unavailable to runtime. Business validation, version checks, outcome record and audit insertion share one transaction under ARCHITECTURE locking; interruption yields a complete permitted state or no effect. Tournament count/seed/start, score/advance/correction, stock/sales and order terminal invariants MUST hold under races and retries.

Privacy and retention are part of this rule. Launch participation is adults18+; admins attest before assigning a participant that they have authority to publish that display name under the operator's stated privacy basis. Store an attestation boolean/time/admin reference internally on assignment (not date of birth or identity document). Pseudonyms are allowed; no address, phone, email, health details, customer identity or payment credentials are collected for players. Account names are administrator labels, not mandatory legal names. Reasons are operational text; entry helpers prohibit health/payment/credential details. The operator publishes its real notice and applicable jurisdictions before deployment. The software makes no assumption that hosting region or EUR selects legal jurisdiction and makes no claim of GDPR or other statutory compliance. Actual legal compatibility is a release attestation; a conflicting obligation requires an owner-policy change before that deployment, never an implementer's guess. Privacy requests are received through the configured privacy contact and verified by the operator outside the app; admins perform the authorized erasure with fresh proof.

Classification: **Public** = deliberate projections (display names remain personal data even when public); **Internal** = commerce/catalog/menu, operational reasons and business operation outcomes; **Restricted** = identity associations, passkey metadata, sessions, invitations, secrets, logs/audit and erasure records. Financial data here means price/quantity totals, never payment account data. All persisted classes use provider-managed encryption at rest with separate KMS keys for database, backups, secrets and audit; IAM restricts decrypt authority. Key rotation annually, secrets rotate on suspected compromise. No application analytics, advertising identifiers or third-party crash collection.

| Record | Retention and erasure |
| --- | --- |
| Tournament/participation/match public names | Two years after completed/cancelled; drafts expire after 180 days without a business edit unless open orders remain (defer expiry and raise a medium operator alert for resolution). At expiry remove public tournament and player-name snapshots; retain only nonpersonal tournament UUID stubs referenced by sales until sales expiry. Active tournaments do not expire automatically |
| Player directory and ranking entries | While assigned to an unexpired tournament/current ranking, or two years after last edit otherwise. Erasure replaces every participation name with `Removed player` plus short UUID, deletes current ranking entries, clears directory name and hides it from selection; existing bracket/result IDs stay referentially intact |
| Account/credential | Until disablement; delete identifying name/public-key material30 days after disablement or immediately on authorized erasure. Keep an opaque actor UUID in retained audit; disable sessions immediately |
| Commerce snapshots, operations/tombstones | Seven years after creation, chosen business retention (not a claimed legal mandate). No customer identity. Referenced inactive catalog/menu records remain as nonpersonal item data. Purge expired sales before tournament stubs |
| Operational reason text |365 days maximum; redact immediately on associated personal-data erasure. Audit retains only reason hash/type, never full reason text |
| Sessions/ceremonies/invitations | Delete24h after expiry/revocation/consumption; operation references retain only safe status/IDs |
| Application/ALB diagnostic logs |30 days, no bodies/tokens/query-string secrets; raw source IP at most7 days then purge; short-lived rate keys are HMAC pseudonyms |
| Sanitized audit events/exports |365 days; S3 Object Lock compliance retention365 days; privacy-minimized opaque IDs/hash/changed-field names only |
| Backups |35 days. Erasure tombstones retained seven years in separate protected recovery storage and replayed before restored data can be served |

Erased player identities are permanently read-only and cannot be renamed or reused. Player erasure preserves anonymous outcomes/statistics but excludes erased players from current rankings and new roster selection. It is the explicit privacy override to read-only archive rules; no score/winner is changed. Account erasure revokes sessions, clears name and credential data and preserves opaque attribution subject to the last-admin safeguard. No public deletion endpoint or automated identity-matching by name. Restores that cannot load/check erasure tombstones remain isolated. Retention jobs must respect foreign keys and preserve financial stubs; expiry itself must not create a publicly accessible stale projection.

**SEC-DATA-02.** Derive all totals, historical price snapshots, normal winners and statistics from authoritative records. Stable operation references are actor/action/content bound; no duplicate stock decrement, sale, completion or advancement under replay. Reject client-supplied computed snapshots and payment credentials/tokens/authorization codes. Authorized price edits affect only future transactions. Cancellation/completion and correction races have one permitted result. Outcome uncertainty is not reported as rollback: reconcile the same reference under FR-8.1. Currency totals remain separate.

## Client containment

**SEC-WEB-01.** Render every supplied name/reason as inert text. No raw HTML, injected SVG, arbitrary props/styles/resource URLs, eval or Function. Only bundled assets and configured safe navigation are permitted. Production CSP: `default-src 'none'; script-src 'self'; style-src 'self'; img-src 'self'; font-src 'self'; connect-src 'self'; base-uri 'none'; object-src 'none'; frame-ancestors 'none'; form-action 'self'; require-trusted-types-for 'script'; trusted-types 'none'`. Bundle external CSS; do not use runtime inline style attributes or script injection. Set X-Frame-Options DENY, X-Content-Type-Options nosniff, Referrer-Policy no-referrer. No embedding is allowed. Trusted Types is defense in depth where supported; unsupported browsers in the supported matrix retain inert-sink/CSP controls, without requiring a polyfill that weakens enforcement. No secrets/source maps/private API records in public artifacts. Non-supported browsers may use public reads when usable but see an unsupported notice; admin workflows require the supported browser matrix.

**SEC-MOBILE-01.** Treat device/local state/native adapter outputs as untrusted. Only network and passkey capabilities; no location, contacts, camera, microphone, push, WebView or custom scheme handler. Disable ordinary Android application backup; iOS credentials use device-only Keychain accessibility. Do not persist business records/forms or session material in AsyncStorage/plaintext. Redact sensitive app-switcher snapshots when admin screens are backgrounded. Clear cache/token on identity change/expired credentials; passkey private keys remain platform-managed. Verify release manifests, native storage and trust settings on iOS and Android hardware. Expo Go is not evidence of native passkey compatibility.

## Runtime and operations

**SEC-RUNTIME-01.** Initial configurable ceilings: body64KiB (ranking.replace128KiB), JSON depth8, object keys64, general strings bound by owner fields, WebAuthn response32KiB, header16KiB, request deadline10s, DB statement5s, lock wait2s, pg pool10 per API task, at most100 concurrent requests/task, worker batch1000. Server aborts/rolls back timed-out transactions; if commit acknowledgement is uncertain use operation lookup. Public read budget6000/min/IP and 12000/min/deployment; ceremonies30/min/IP and 10/min/account-or-invitation when known, plus1000/min/deployment; authenticated business commands120/min/account and 600/min/deployment. Fixed windows are counted atomically in Postgres using privacy-preserving bucket keys, TTL one hour; security state unavailability denies protected work. The published load profile distributes five mutations/sec among25 admins, within these budgets. Initial ceilings are chosen design defaults, not capacity evidence: load/adversarial tests must demonstrate the REQUIREMENTS target before release and any tuning must preserve that target. Retry policy is bounded by REQUIREMENTS;429 honors Retry-After without exceeding its attempt cap. No CAPTCHA or automatic account lockout.

Use strict HTTP parsing, nonroot containers with read-only filesystem and bounded writable tmpfs, no host sockets, no shell/dynamic execution with untrusted input, no inspector/debug ports, minimal Linux capabilities. API egress/DB authority follow ARCHITECTURE. Node permission features are optional defense in depth only, not a sandbox claim. Missing/invalid secrets, origin, signing trust or required runtime security configuration prevents readiness. Production diagnostics never include memory dumps, bodies or environment secrets.

**SEC-OPS-01.** Record authentication/credential/invitation/grant events, denials, validation/limit failures, and every supported admin mutation. Event fields: UUID, sequence, UTC time, actor opaque UUID when known, action, target UUID/type, request/operation UUID, outcome code, changed-field names, reason_type and SHA-256 reason hash when applicable; no actual names, text bodies, token/credential bytes or full IP. Sanitize/encode log values, cap event payload4KiB. This provides attributable changes, not proof the entered score was true. Mutation events and outbox append are in the business transaction; failure to durably record rolls it back. Denial/read-failure logs use a bounded local buffer/cloud sink; its failure denies no public data but raises an operational alert and never authorizes a protected request.

The append-only audit function assigns a serialized sequence and SHA-256 chain over canonical event JSON plus prior hash; runtime cannot update/delete rows. Worker exports at least every minute to separate KMS-encrypted S3 objects, Object Lock365 days, writer role without delete. Every five minutes compare contiguous sequences, chain hashes, export checkpoint and object digests. Retention role may purge DB copies only after verified export and 365 days; S3 lifecycle removes objects after lock expiry. Tampering, missing chain links and failed exports are observable; no claim of immunity to ultimate cloud-root compromise. Restore/maintenance actions use separate operator audit events. Export credentials cannot rewrite the database history.

Vulnerability reports go to the real configured SECURITY_CONTACT, shown in public deployment information. Acknowledge within 2 business days; triage critical within 24h and other reports within 5 business days. Release owner jmanico initially also owns incident coordination; deployment manifest names the current reachable operator/on-call. No external message is sent by this specification task.

**SEC-SUPPLY-01.** Lock direct/transitive dependencies and reviewed install scripts; frozen-lock mismatch fails, never silently updates. pnpm install first uses `--frozen-lockfile --ignore-scripts`; explicit reviewed `onlyBuiltDependencies` allowlist controls later rebuilds. Assess `pnpm audit --json`, GitHub dependency review/Dependabot and OS/native advisories; build container/native SBOMs using CycloneDX format and capture tool versions/digests. Applicable high/critical findings MUST be fixed before promotion, no accepted launch exception. CI uses minimal permissions, pinned action SHAs, isolated untrusted-PR checks and environment-scoped OIDC for deployments. Reproduce artifacts from clean checkout/locked resolution; record runtime, OS/native SDK, lock hash, reviewed scripts, advisories, tests, artifact digests and signing provenance. No debug interfaces/signing keys in shipped artifacts. Dependency update PRs are weekly; security updates are prioritized by severity.

**SEC-FAIL-01.** Deny unavailable/failed identity, authorization, validation and security configuration decisions with safe protocol errors and no unauthorized state or sensitive side effect. Distinguish a pre-admission rejection from an unknown result after commit may have occurred. No launch fail-open exception exists. Future exceptions require an explicit SECURITY owner change with scope, reason, compensating control, owner and expiry; a filled template or implementation convenience cannot authorize one.

## Security verification

All security-critical decisions and error paths MUST have positive and negative tests. Each implementation issue includes its own applicable control tests; none are deferred to a generic security cleanup. Release additionally exercises real supported passkey platforms, concurrent transactions/replay/lost acknowledgements, injected DB/audit/security-decision failures, public field allowlists, hostile text/CSRF/framing, session revocation/late responses, native storage/manifests/TLS, configured limits/load, audit tampering, backup restore/erasure replay and locked artifact inspection. Coverage means every security decision branch/error path is demonstrated, not an arbitrary whole-project percentage. Evidence records fixture, expected/actual result, tool/build versions and artifact hash. A document check cannot satisfy these implementation tests.

Assurance target: the complete project control set above plus the verified ASVS5.0.0 mappings below; **no blanket ASVS level certification is asserted or required**. This bounded target avoids treating unassessed controls as verified.
