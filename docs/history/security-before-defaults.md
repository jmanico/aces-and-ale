## Access and Disclosure Policy

**SEC-ACCESS-02 — Required disclosure/grant matrix.** Source: human decisions of 2026-10-13 for tournaments and the four requested administrative action groups; commerce/internal-data and start-operation grants below are minimal launch decisions under the user's delegated scope. An admin means an account with a trusted server-established grant, not a client actor label. Other actor categories do not confer additional permissions. For tournament planning, the organizer means an admin exercising this existing grant; interview Q005 (2026-10-13) places ranking-list selection within that workflow.

| Surface / operation | Grant and disclosure |
| --- | --- |
| Tournament read, including a newly created empty/incomplete draft | Anonymous and authenticated read from creation. Deliberate public projection: tournament reference/state, assigned participant display names and match references/competitors, plan, scores/results and derived tournament statistics under FR-1–FR-5. Additional tournament fields require explicit classification before exposure. |
| Create tournament, assign participants, enter/change plan (including choosing its external seeding ranking list and manually entering its player rankings), enter/correct scores/results | Authenticated admin only. |
| Start play | Authenticated admin only; business preconditions remain in FR-1.1. |
| Catalog/menu and stock administration, stock adjustments, merchandise sales, order creation/completion/cancellation, commerce reads/totals/history | Authenticated admin only for launch. No public commerce catalog/menu or extra staff role is introduced. |
| World/local ranking reads | Anonymous/authenticated reading of the deliberate ranking representation in FR-4.1/4.2; underlying source records are not implicitly public. |
| Account/credential/session records, account-player links, privileges, audits/diagnostics and operational metadata | Excluded from public representations. Only explicitly authorized identity/operational handling may access them; admin status alone is not a blanket diagnostic/secret-access grant. Detailed grants: TO BE DECIDED. |
| Unspecified operations (including registration eligibility/admin provisioning) | No implied grant; explicit policy required before enabling them. |

Responses MUST project deliberately allowed fields rather than serialize whole domain/persistence objects. Tournament publicity does not publish account associations or commerce records. Public identifiers are references, not secrets or access tokens. Unauthorized protected requests MUST have no protected state change or sensitive side effect and MUST not disclose protected fields or distinguish inaccessible from nonexistent protected objects unnecessarily. Exact protocol response forms: TO BE DECIDED.

**Acceptance criteria:** Anonymous read of a zero-player draft returns its public fields without identity/commerce/diagnostic fields. Admin requests satisfying functional preconditions succeed for each granted operation; anonymous and authenticated nonadmin requests fail without change, including direct requests, substituted object references and privilege fields. Public ranking responses expose only their defined representation. Internal commerce reads fail for anonymous/nonadmin requesters. Field-substitution attempts cannot add ungranted fields or reveal internal records.

## Threat Model

**ASSUMPTION:** Consider unauthenticated requesters, authenticated users exceeding their eventual permissions, malicious browser content, modified mobile clients, network attackers, and compromised dependencies or operational credentials. These are threat scenarios, not allegations about the listed actors. Deployment exposure, likelihood, impact ratings, and accepted residual risk are TO BE DECIDED. An otherwise authorized admin may also misuse granted operations; this is a capability scenario, not an allegation.

**ASSUMPTION:** Protect the integrity and permitted disclosure of the application-owned tournament, participant, match, plan, score, statistics, and ranking data. Passkey account associations, credential records, session material, configuration secrets, and security logs are additional security assets whose schema and storage are TO BE DECIDED. Commerce catalog/menu, stock, order/sale history, price snapshots and totals defined in [REQUIREMENTS.md](https://github.com/jmanico/aces-and-ale/blob/5f1aa04e24003b840ca1f2de397973f3bb90ac91/REQUIREMENTS.md) are additional integrity assets; commerce records are internal under SEC-ACCESS-02.

## Security Requirements

**SEC-AUTH-01 — Passkey-only authentication.** All user authentication MUST use passkeys, including authentication by any actor category later granted administrative permissions. Password, email/SMS code, magic-link, or other non-passkey sign-in fallbacks MUST NOT be introduced. This policy does not determine which views require sign-in. Service-to-service and operational identities are UNKNOWN; their policy is TO BE DECIDED. Source: human Security Notes.

**SEC-AUTH-02 — Registration encouragement.** Registration MUST encourage setting up access on two devices. The second device is encouraged, not a mandatory registration gate. Exact interaction, supported devices, and enrollment tracking are TO BE DECIDED. A synced passkey can be available on several devices, so credential count cannot be treated as proof of two independent recovery methods. Source: human Security Notes and [FIDO passkey synchronization guidance](https://fidoalliance.org/passkeys/).

**SEC-AUTH-03 — ASSUMPTION: proposed passkey verification.** Use a maintained WebAuthn-compatible verifier in the application; library and native integration are TO BE DECIDED. Bind cryptographically random, expiring, single-use challenges to the ceremony and intended account context. Verify ceremony type, challenge, expected origin, RP ID, account/credential association, required presence/verification flags, algorithms, registration response, and assertion signatures before accepting authentication. Prevent reuse and cross-account credential attachment. **ASSUMPTION:** Require user verification for passwordless ceremonies; policy confirmation is TO BE DECIDED. RP ID, origin allowlist, attestation policy, challenge limits, expiry, and authenticator compatibility are TO BE DECIDED. This is a project proposal derived from [WebAuthn Level 2, registration](https://www.w3.org/TR/2021/REC-webauthn-2-20210408/#sctn-registering-a-new-credential) and [assertion verification](https://www.w3.org/TR/2021/REC-webauthn-2-20210408/#sctn-verifying-assertion), not a custom cryptographic protocol.

**SEC-AUTH-04 — ASSUMPTION: credential lifecycle and recovery.** Require recent successful passkey verification before adding or removing a credential on an existing account; protect these operations against request forgery and account substitution. Freshness, initial registration/bootstrap, revocation, last-credential removal, and all-devices-lost recovery are TO BE DECIDED. Recovery must be reconciled with SEC-AUTH-01 before implementation; no weaker fallback or support override is implicitly authorized. Authentication records must not equate player names with unique account identities.

**SEC-ACCESS-01 — Server authority.** The API MUST independently authorize each protected operation and object using trusted server context. Client roles, hidden controls, route state, object references, and native assertions grant no authority. Reject unvalidated privilege/ownership fields rather than binding request bodies directly to records. Deny protected operations lacking an explicitly defined grant under SEC-ACCESS-02. Exact protocol rejection form remains TO BE DECIDED; the no-change/no-disclosure outcome is required. Sources: S-JS, S-REACT, S-NATIVE.

**SEC-INPUT-01 — Runtime validation.** Validate incoming commands, API responses at clients, stored client values, and configuration at their receiving boundary. Use allowlisted security-sensitive fields and bound types, bytes, structure, collections, and computational cost. Reject prototype-polluting keys; keep untrusted data out of dynamic execution and module selection. Type annotations cannot substitute for runtime checks. **SEC-DATA-02 — Required launch integrity.** Independently derive sale/order snapshots, totals and statistics from validated authoritative records under FR-5–FR-8.
